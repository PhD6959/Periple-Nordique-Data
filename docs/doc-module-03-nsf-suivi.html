Rubriques saisonnièresCols et routes à fermeture saisonnière · Péages et badge · Restrictions de dégel · Routes de glace · Règles de circulation hors réseau public — une donnée collectée aujourd'hui sera fausse au départ du 15 avril 2027. Ces rubriques ne sont jamais « acquises » : elles doivent être revérifiées dans les semaines précédant le départ, même affichées comme terminées.

Comment ce document est produit

Il est engendré à partir de manifest-donnees.json, qui décrit chaque rubrique : source, licence, fichier, date de collecte, nature, responsable et état par pays. Le tableau ne peut donc pas diverger du manifeste. Toute correction se porte dans le JSON, puis le document est régénéré.

Pourquoi un manifeste plutôt qu'un tableau tenu à la main Le tableau de traductions du module 05 islandais, saisi à la main, portait un numéro de version décalé d'un cran par rapport à l'application. Un document tenu à la main diverge. Le manifeste supprime cette classe d'erreur — et il pourra en outre être lu par l'application elle-même, pour afficher la fraîcheur de chaque couche, voire masquer une couche non publiée.

Enchaînement des états

Les états sont séquentiels : la publication sur GitHub précède l'intégration dans l'application, puisque le module lit ses couches depuis le dépôt. Deux états terminaux ne sont pas des échecs : traité par lien, quand aucune donnée ouverte n'existe et qu'on renvoie vers le service officiel, et sans objet, quand la rubrique n'a pas de sens pour un pays.

Structure des fichiers de données

Un fichier GeoJSON par rubrique, les trois pays confondus, avec une propriété country sur chaque entité. Un fichier par rubrique et par pays multiplierait par trois le nombre de requêtes au chargement sans rien apporter.

Hébergement

Le dépôt actuel s'appelle Meteo-Islande-Feroe-Data. Deux voies : un dossier sources/nordique/ dans ce dépôt, ou un dépôt neuf. Décision en attente. Le manifeste et les fichiers de données ont vocation à vivre à la racine du dossier de données, quel que soit le choix retenu.

Ce qu'il faut écrire, selon le cas

Nouveau script de collecte ou de conversion

  • Bandeau en tête du script : ce qu'il fait, la source, ce qui a été constaté, ce qui reste incertain, comment le lancer
  • Une ligne dans outils/README.md du dépôt de données, dans la section du pays ou de la source
  • Les pièges rencontrés dans la section « Pièges » de cette même source
  • Le script lui-même versé dans outils/, jamais laissé dans le dossier de travail

Nouvelle couche de données publiée

  • Une rubrique au manifeste : source, licence, date de collecte, volume, pièges évités, réserves
  • Un bloc « verification » dans cette rubrique : scripts à rejouer, volume attendu, ce qu'il faut contrôler
  • Une section au README du dépôt de données si la licence est nouvelle
  • Une entrée dans la table LAYERS du module 3 et les libellés dans les six langues

Révision d'un module applicatif

  • Journal des changements dans le bandeau en tête du module
  • Version incrémentée aux trois endroits : nom du fichier, bandeau, constante VERSION
  • outils/generer-listes.sh lancé, pour que le service worker et le menu suivent
  • README du dépôt applicatif si un écart de conception change

Changement de structure interne d'un module météo

  • docs/modules-meteo.md du dépôt applicatif : la structure touchée, le motif, ce qui reste incertain

Nouvelle source de données interrogée

  • Rubrique sources_api du manifeste : point d'accès, forme des requêtes, licence, types vérifiés avec leur version
  • Ce qui a induit en erreur, explicitement — une documentation tierce périmée coûte des heures

Décision, arbitrage, ou renoncement

  • Question ouverte au manifeste, avec le constat, ce qui a été essayé, ce qui ne l'a pas été, et la conséquence
  • Un renoncement se documente aussi soigneusement qu'une réussite : sans quoi la reprise refait les mêmes tentatives

PrincipeToute donnée extraite a une date de collecte, portée par la propriété « updated » de chaque entité et par « collecte_le » de chaque rubrique. Une donnée de septembre 2026 n'est pas fausse en avril 2027, mais elle n'est plus à jour : des routes ferment, des bacs changent d'horaire, des restrictions de dégel se publient. Les rejouer coûte quelques heures et donne une certitude.

Signes qu'une source a changé

  • Un script renvoie zéro entité là où il en renvoyait des milliers : l'adresse ou le nom de couche a changé.
  • Un script renvoie un volume très différent : le filtre ne porte plus sur les mêmes champs.
  • Une réponse en HTML au lieu de JSON : page d'erreur du serveur, souvent temporaire.
  • « ObjectType does not exists » côté suédois : il manque l'attribut namespace, ou la version de schéma a changé.
  • Un champ attendu absent : le schéma a évolué. Les scripts de profil le montrent, les scripts de conversion non — relancer le profil avant la conversion.
RègleNe jamais publier une couche dont le rapport de conversion n'a pas été lu. Chaque script produit un rapport qui dit les volumes, les écarts et les anomalies. C'est ce rapport qui décide, pas l'absence de message d'erreur.

Zones protégées norvégiennes — contours

Le service Naturvernområder de Miljødirektoratet expose six couches. Les deux qui portent les zones — naturvern_omrade et naturvern_klasser_omrade — répondent « Application Error : Could not access any server machines » alors que les autres couches du MÊME service fonctionnent. Panne partielle et persistante côté serveur, constatée deux fois le 12/09/2026 à plusieurs minutes d'intervalle, et non une erreur de requête. Repli examiné : la couche 3, naturvern_grense, répond et compte 27 735 LineString. Mais ce sont des segments de limite SANS NOM ni rattachement à la zone qu'ils bordent : on saurait qu'une limite passe là, sans savoir de quelle zone. Écarté d'un commun accord : une information dégradée à ce point ne vaut pas 27 735 entités.

À creuserRéessayer le service de Miljødirektoratet, la panne pouvant se résoudre d'elle-même.
